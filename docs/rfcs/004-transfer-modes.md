# RFC 004: Transfer modes and fidelity

Status: accepted and implemented for visible-history continuity; richer event fidelity remains partial

Planner chooses safest available mode:

1. Native resume or fork for same provider.
2. Official documented import.
3. Verified native materialization for supported provider versions.
4. Semantic handoff into a fresh target session.
5. Portable export/import through a redacted canonical bundle.

An in-place continuation of a Cursor IDE chat uses the `open_workspace` mode. The native conversation stays in Cursor. The desktop launcher opens the folder, and the operator selects the original chat from Show Chat History.

OmniSession implements native resume and fork, provider-owned imports for Codex, OpenCode, Grok, and Hermes, version-gated private writers for Claude Code, Pi, Antigravity CLI, Cursor Agent, and Cursor IDE, semantic handoff, and portable export/import. Native target imports preserve visible user and assistant history. Complete tool call/result pairs become historical native tool records in writers that declare them (Claude Code, Pi, Hermes, OpenCode, and Grok), named `hist_<provider>_<tool>` and never re-run; other bounded tool records stay documentary messages. OpenCode receives each pair as an assistant message with a `tool` part in `completed` or `error` state. That v2 part schema predates `opencode import`, which stores parts as exported, so no separate version gate applies. Later conformance reports expand to files, subagents, permissions, checkpoints, plans, and attachments. Status is `preserved`, `summarized`, `historical_only`, `redacted`, `omitted`, or `unsupported`.

When Claude rewinds a conversation, OmniSession follows the selected message and its parents. The reader keeps selected messages and results in conversation order. It inserts missing blocks beside surviving parts of the same response and uses the message, request, and writer IDs to distinguish retries. A tool result can identify its call by its parent record or by the UUID of the assistant that issued it. OmniSession checks the call, response, and writer for results on the selected branch and for parallel results. It considers only calls that existed when the result arrived. After a verified compaction, copying an earlier record leaves the checkpoint and its continuation selected. When the checkpoint retained messages, a newly written message whose parent was omitted starts a continuation after them. A progress record points to its conversation ancestor even if Claude wrote the progress record after the boundary. An explicit root starts an independent conversation.

If the checkpoint removed an attachment, a new message that names it follows the retained conversation, even when the attachment had no parent. If the checkpoint kept the attachment, the new message branches at its retained position. A progress record can identify the same attachment.

A Claude attachment or turn-duration record can survive a compaction that removed its parent. The removed parent can itself be a root attachment. OmniSession treats an identical copy of a supported record with a verified parent as the same occurrence. Updating only a turn-duration record’s elapsed time also preserves that occurrence. For a new record, it checks the record's timestamp against the selected summary on the same conversation branch. If the summary was the eligible same-side record within the previous five seconds and the record order is verifiable, the handoff carries that summary and the new turn. If the records establish only that the parent was removed, the active handoff starts at the new turn. In both cases, the handoff reports partial coverage and directs the receiving agent to the earlier verified context in the private recovery file. A disconnected branch or an unsupported summary cannot restore the removed reply.

When a checkpoint explicitly retained no messages and removed the parent of a new turn, Claude Code 2.1.322 can reconnect that turn using timestamps. It uses the latest eligible record on the same side of the session at most five seconds earlier. If several eligible records share a timestamp, their original order breaks the tie. The handoff starts at the new turn when the source timestamps establish a break. Earlier verified context remains available in the private recovery file. If the reader cannot verify the necessary records, timestamps or order, it reports partial history.

Within the selected history, repeating a terminal message selects it. Repeating a message that has children selects its most recently created descendant. When a later native sequence contains every earlier identified record with the same contents, the reader checks that its first occurrences still follow their parents, tool calls, and retained compaction records before using its order. Earlier fragments can overlap. For large files with two byte-identical copies of a complete, explicitly linked native sequence, the reader can reduce the sequence once and charges both copies against the physical record limits. This resolves tool issuers, retained messages and progress links against the same copy. If different assistant records share a UUID, only a version supported by the selected history can supply a missing block. When both results identify the same call, the selected result takes precedence.

Older Claude conversations recorded without parent links keep their file order. Once an identified conversation uses parent links, a new identified record with no parent field starts independently, unless a compaction explicitly declares it as its summary. A progress record preserves that same root. If its parent names an unknown UUID, the full reader keeps the connected messages and reports the missing parent. Native Claude can use a nearby timestamp to reconnect an unknown UUID. OmniSession keeps that context out of the active handoff when the original branch cannot be verified. Progress records have a separate limit so they can connect message parents in long sessions. A malformed record produces a coverage warning, including when Claude has written only part of the last record. A preview keeps head messages when the tail links to them, including when the tail repeats a complete exchange. For a short gap, it can read up to 4 MiB or 65,536 rows of progress, attachment and turn-duration links to establish that ancestry. When it cannot connect the samples, it keeps the verifiable tail and reports partial coverage. Workspace and branch metadata come from the main session.

When Claude compacts a conversation, it can retain messages that it wrote before the summary. OmniSession checks the entire retention list before using it to follow a rewind. All listed UUIDs must identify supported records that existed before the boundary. If the list is incomplete or ambiguous, the reader follows the available parent chain and marks coverage as partial. A progress record can link a result to its assistant, but Claude cannot restore progress as a retained message. If a marked Claude compaction anchor has no summary text after the reader removes the standard envelope, the native handoff reports partial coverage. A verified retention list still selects the conversation when an older message is copied later. The handoff keeps the verified retained records and subsequent messages. The recovery file includes the earlier available context. If a continuation names a missing summary or one of its verified retained records, the reader preserves the retained messages and continuation and reports the missing summary. A continuation attached directly to the boundary precedes those retained messages. If the file ends at the boundary, a valid retention list selects the remaining messages. If the boundary identifies the anchor but the summary flag is missing, the reader keeps a recognizable summary as an assistant checkpoint and reports partial coverage. Unrecognized anchor text stays in the recovery file. A rewind can return to an earlier valid summary. If a later rejected checkpoint makes its retained branch uncertain, the active handoff follows the recorded parents and reports partial coverage. The private recovery file preserves the earlier verified summary and retained conversation.

A valid compaction supplies the order of messages after the summary. A rewind can keep several blocks of the same response. OmniSession identifies those blocks within their originating user turn, even if a later turn reuses the same response identifiers. Search and recovery exclude discarded requests and replies, including after a later compaction. A later summary can explicitly list a request that a rewind withdrew. Claude Code can show that request again. OmniSession follows the selected branch and reports the conflicting retention record.

A retained result stays in documentary history when its call has been summarized, including when a parallel result links it to the original response. If a selected result names a missing assistant, or the named assistant lacks the matching tool call, OmniSession preserves the output as documentary history and reports partial coverage. A tool result and a user request can share a Claude record. After a rewind discards the request, the verified tool result survives. If a later compaction retains both the old row and the competing replacement, OmniSession reports the conflict. Other calls with verified results keep their native pairs. If selected outputs disagree about the same call, or a selected output could come from several calls with the same ID, OmniSession preserves the verifiable pairs and reports partial coverage. The fidelity report marks earlier conversation as summarized and warns when an import limit cuts off history.

When a cross-provider import loses context to an import limit, an incomplete source, or a compaction with earlier history still available, OmniSession writes a private Markdown file in the local temporary directory. The file includes the available redacted messages in conversation order. The native target receives the path as historical assistant text, including with `--materialize-only`. Read-back verification covers that reference. A semantic fallback passes the path in its launch prompt. The file stays available for later resumes until the user or the operating system removes it.

No transfer silently upgrades to a riskier mode. Unsupported native imports use semantic handoff before writing. Failed writes stop after an exact rollback attempt, instead of launching a second transfer with uncertain state. Private-format writing remains disabled below accepted minimum versions in RFC 007. Structural validation and read-back catch incompatible newer formats.

Assistant replies can contain agent instructions, including a requested `AGENTS.md` document. OmniSession keeps those replies in visible history and quotes them in handoff files. The semantic handoff and recovery file take the next action from the latest recognized plan update. An empty or completed plan clears an earlier action.

Codex adds a display notification after imported messages. A literal assistant reply with the same text has its own response item. Older portable bundles sometimes discarded that response item. OmniSession identifies the notification at the end of the imported messages by its following cumulative token count. Earlier replies and subsequent native turns retain their original order. OmniSession versions through v0.8.34 discarded that count, even if the session later resumed. When a display record could be either an authored reply or the notification, the transfer reports incomplete history. The recovery file lists the unresolved record by source sequence number.

`omni handoff SESSION` prepares context for a manual transfer into a chat app. It saves the full private Markdown export with continuation instructions, source-harness provenance, session and workspace details, bounded redacted visible history, and historical tool activity. The clipboard gets a separate compact message capped at 4,000 UTF-8 bytes, an OmniSession safety bound rather than a claimed provider limit. It includes the first three and last two available user or assistant messages, marks omitted middle messages and shortened excerpts, and leaves out tool activity. It includes the saved local path for the user to attach the full export manually; a chat app cannot read that local path from the pasted message. The command reports the saved path and copy result without printing transcript content. The file persists after exit, including when clipboard access fails. This operation does not create a native target session, change routing bindings, or carry forward historical approvals.
