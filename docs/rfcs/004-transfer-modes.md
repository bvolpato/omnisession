# RFC 004: Transfer modes and fidelity

Status: accepted and implemented for visible-history continuity; richer event fidelity remains partial

Planner chooses safest available mode:

1. Native resume or fork for same provider.
2. Official documented import.
3. Verified native materialization for supported provider versions.
4. Semantic handoff into a fresh target session.
5. Portable export/import through a redacted canonical bundle.

OmniSession implements native resume and fork, provider-owned imports for Codex, OpenCode, Grok, and Hermes, version-gated private writers for Claude Code, Pi, Antigravity CLI, Cursor Agent, and Cursor IDE, semantic handoff, and portable export/import. Native target imports preserve visible user and assistant history. Complete tool call/result pairs become historical native tool records in writers that declare them (Claude Code, Pi, Hermes, OpenCode, and Grok), named `hist_<provider>_<tool>` and never re-run; other bounded tool records stay documentary messages. OpenCode receives each pair as an assistant message with a `tool` part in `completed` or `error` state. That v2 part schema predates `opencode import`, which stores parts as exported, so no separate version gate applies. Later conformance reports expand to files, subagents, permissions, checkpoints, plans, and attachments. Status is `preserved`, `summarized`, `historical_only`, `redacted`, `omitted`, or `unsupported`.

When Claude rewinds a conversation, OmniSession follows the selected message and its parents. The reader keeps selected messages and results in conversation order. It inserts missing blocks beside surviving parts of the same response and uses the message, request, and writer IDs to distinguish retries. A tool result can identify its call by its parent record or by the UUID of the assistant that issued it. OmniSession checks the call, response, and writer for results on the selected branch and for parallel results. It considers only calls that existed when the result arrived. When both results identify the same call, the selected result takes precedence.

Older Claude records without parent links keep their file order. If a stored parent is missing, the full reader keeps the connected messages and reports that it cannot verify earlier history. Progress records have a separate limit so they can connect message parents in long sessions. A malformed record produces a coverage warning, including when Claude has written only part of the last record. A preview keeps head messages when the tail links to them. For a short gap, it can read up to 4 MiB or 65,536 rows of progress and attachment links to establish that ancestry. When it cannot connect the samples, it keeps the verifiable tail and reports partial coverage. Workspace and branch metadata come from the main session.

When Claude compacts a conversation, it can retain messages that it wrote before the summary. OmniSession checks the entire retention list before using it to follow a rewind. All listed UUIDs must identify supported records that existed before the boundary. If the list is incomplete or ambiguous, the reader follows the available parent chain and marks coverage as partial. A progress record can link a result to its assistant, but Claude cannot restore progress as a retained message.

A valid compaction supplies the order of messages after the summary. A rewind can keep several blocks of the same response. OmniSession identifies those blocks within their originating user turn, even if a later turn reuses the same response identifiers. Search and recovery exclude discarded requests and replies, including after a later compaction.

A retained result stays in documentary history when its call has been summarized. Other calls with verified results keep their native pairs. If selected outputs disagree about the same call, or a selected output could come from several calls with the same ID, OmniSession preserves the verifiable pairs and reports partial coverage. The fidelity report marks earlier conversation as summarized and warns when an import limit cuts off history.

When a cross-provider import loses context to an import limit, an incomplete source, or a compaction with earlier history still available, OmniSession writes a private Markdown file in the local temporary directory. The file includes the available redacted messages in conversation order. The native target receives the path as historical assistant text, including with `--materialize-only`. Read-back verification covers that reference. A semantic fallback passes the path in its launch prompt. The file stays available for later resumes until the user or the operating system removes it.

No transfer silently upgrades to a riskier mode. Unsupported native imports use semantic handoff before writing. Failed writes stop after an exact rollback attempt, instead of launching a second transfer with uncertain state. Private-format writing remains disabled below accepted minimum versions in RFC 007. Structural validation and read-back catch incompatible newer formats.

`omni handoff SESSION` prepares context for a manual transfer into a chat app. It saves the full private Markdown export with continuation instructions, source-harness provenance, session and workspace details, bounded redacted visible history, and historical tool activity. The clipboard gets a separate compact message capped at 4,000 UTF-8 bytes, an OmniSession safety bound rather than a claimed provider limit. It includes the first three and last two available user or assistant messages, marks omitted middle messages and shortened excerpts, and leaves out tool activity. It includes the saved local path for the user to attach the full export manually; a chat app cannot read that local path from the pasted message. The command reports the saved path and copy result without printing transcript content. The file persists after exit, including when clipboard access fails. This operation does not create a native target session, change routing bindings, or carry forward historical approvals.
